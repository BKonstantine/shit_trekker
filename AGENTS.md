# Инструкции для Codex — ShitTracker

## Контекст проекта
ShitTracker — небольшой приватный таск-трекер для нескольких пользователей. Пользователи вручную собирают в одном месте рабочие задачи, пришедшие из чатов, Jira, Mattermost, почты и других каналов. **Автоматических интеграций и AI в MVP нет.** Перед изменениями прочитай `docs/PRODUCT.md`, `docs/ARCHITECTURE.md` и документ по затрагиваемой области. Принятые решения находятся в `docs/DECISIONS.md`; если требования противоречат друг другу, приоритет имеют более новые явные указания пользователя.

## Правила работы
- Реализуй **только запрошенный объём** небольшими изменениями, удобными для проверки. Не выполняй весь roadmap без отдельного согласования.
- До изменений изучи текущий код и доступные команды. Предлагаемые структуры каталогов — ориентир, а не повод перестраивать уже работающий проект.
- Если важное архитектурное решение или вопрос безопасности не определён, объясни варианты и уточни выбор до существенного усложнения реализации.
- Не внедряй SSR, Next.js, Nuxt, NestJS, Fastify, Nx и Turborepo без прямого запроса.
- Не добавляй неиспользуемые зависимости, преждевременные абстракции, универсальные фреймворки и пустые FSD-слайсы.
- Используй TypeScript в строгом режиме; валидируй недоверенные серверные данные через Zod. По возможности запускай соответствующие typecheck, lint, тесты и сборку и честно сообщай результаты.
- Не коммить учётные данные, реальные пользовательские данные и секреты из `.env`. Не выполняй `push` и развёртывание без явного запроса.
- Если изменяется поведение продукта или архитектура, одновременно обновляй соответствующие `docs/*.md`.
- Пиши объяснения, планы, комментарии к изменениям и документацию **по-русски**. Названия файлов, идентификаторы, команды, имена классов, HTTP-поля и стандартные технические термины оставляй на английском, где это уместно.

## Утверждённый технический стек
- Монорепозиторий: **pnpm workspaces**, `apps/web`, `apps/api`, `packages/shared`. Без Nx/Turborepo.
- Frontend: **React + TypeScript + Vite**, **Ant Design** с тёмной темой и сиреневыми акцентами; SCSS по необходимости. Архитектура **FSD**. Статический адаптивный SPA.
- Backend: **Node.js + Express 5**, модульный монолит, **SQLite + Drizzle**, **Zod** для контрактов и валидации.
- Авторизация: **серверные сессии**, защищённые HttpOnly-cookie; учётные записи создаются администратором вручную через CLI. Публичной регистрации нет.
- Сервер: **Repka Pi 3, 2 ГиБ RAM**. Планируем удалённый доступ по HTTPS через Cloudflare Tunnel; совместимость с конкретной ОС и ARM нужно проверить.
- `packages/shared` содержит DTO и транспортные Zod-схемы; Drizzle-схемы базы данных остаются исключительно на backend.

## Критически важные правила продукта
- Каждый пользователь имеет доступ **только к своим** задачам и источникам. Администратор тоже не видит чужие задачи через обычный интерфейс/API.
- Backend извлекает `userId` из проверенной сессии, а не из данных клиента. Каждый запрос чтения и изменения учитывает одновременно ID объекта и ID владельца. Тесты обязательно проверяют межпользовательскую изоляцию.
- У задачи есть **обязательный дедлайн в виде календарной даты** (`YYYY-MM-DD`) и статус `new`, `in_progress` либо `done`. Даты в прошлом допустимы. Просрочка вычисляется для незавершённых задач и **не является отдельным статусом**.
- Источники создаются пользователем: ID, название, ключ иконки. Их можно добавлять и редактировать. Источник, к которому привязаны задачи, удалить нельзя (`HTTP 409`).
- Счётчики рядом с источниками слева показывают **незавершённые** задачи текущего пользователя; общий список может включать и завершённые.
- Десктоп: левый сайдбар с источниками, центральная таблица задач, боковая форма создания/редактирования. Телефон: карточки, выдвижное меню источников, полноэкранная форма.
- В MVP нет breadcrumbs, рабочих пространств, Kanban, совместных задач, автоматических интеграций, уведомлений, AI, импорта/экспорта через UI и публичной регистрации.

## Соглашения по frontend (FSD)
- `src/app` — инициализация приложения, провайдеры, маршруты, тема.
- `src/pages` — страницы (`login`, `tasks`).
- `src/widgets` — крупные блоки интерфейса (сайдбар, таблица задач).
- `src/features` — действия пользователя (вход, форма задачи, изменение статуса, редактор источника).
- `src/entities` — модели предметной области, запросы и базовое представление (`task`, `source`, `user`).
- `src/shared` — универсальная API-инфраструктура, UI-примитивы, утилиты, конфигурация. Без бизнес-логики задач и источников.
- Импортируй слайсы через их публичный `index.ts`. Не делай прямые импорты между слайсами одного слоя; нижние слои не импортируют верхние. Компоненты Ant Design можно импортировать напрямую, если обёртка не добавляет реальной ценности.

## Соглашения по backend
- Организуй код по предметным модулям: `auth`, `users`, `tasks`, `sources`.
- Модуль при необходимости может содержать routes/controller/service/repository; не создавай лишние файлы ради формального соответствия структуре.
- Схема БД и миграции находятся в `apps/api`, не в frontend или `packages/shared`. Контроллеры не содержат SQL; проверка владения ресурсом обязательна на стороне backend.
- Изменяющие запросы защищены авторизацией и от CSRF; вход ограничен по частоте попыток. Для чужого ресурса предпочтительно отвечать `404`, не раскрывая его существование.
- Резервные копии production-базы SQLite — задача серверной эксплуатации, а не пользовательская функция экспорта/импорта.
