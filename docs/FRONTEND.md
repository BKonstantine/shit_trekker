# Frontend — React, FSD, Ant Design

## Стек
React + TypeScript + Vite; Ant Design с `ConfigProvider`, `theme.darkAlgorithm` и кастомными design tokens; SCSS точечно. Клиентский рендеринг и статическая сборка. Без Next.js и SSR.

## Предлагаемые FSD-слайсы (создавать по мере необходимости)

```text
apps/web/src/
├── app/
│   ├── providers/         # тема Ant, QueryClient при необходимости
│   ├── router/            # маршруты login и tasks, если добавлен роутер
│   ├── styles/
│   └── App.tsx
├── pages/
│   ├── login/
│   └── tasks/
├── widgets/
│   ├── app-sidebar/
│   └── task-table/
├── features/
│   ├── sign-in/
│   ├── task-editor/
│   ├── change-task-status/
│   └── source-editor/
├── entities/
│   ├── task/
│   ├── source/
│   └── user/
└── shared/
    ├── api/
    ├── ui/
    ├── lib/
    └── config/
```

При необходимости слайс включает `ui/`, `model/`, `api/` и публичный `index.ts`. Не создавай пустые каталоги заранее. Верхние слои используют нижние, но не наоборот; избегай прямых импортов между разными слайсами одного слоя. В `src/shared` не должно быть бизнес-логики. `packages/shared` — **пакет монорепозитория**, а не FSD-слой.

## Компоненты и взаимодействия
- **Десктоп:** `Layout`, `Sider`, `Table`, `Select`, `Input.Search`, `Button`, `Dropdown`, `Tag`, `Empty`.
- **Создание/редактирование задачи:** один `Drawer` с `Form`; обязательный `DatePicker`, `Input.TextArea`, выбор источника и необязательная ссылка на оригинал. При закрытии формы с несохранёнными изменениями запрашивать подтверждение.
- **Создание/редактирование источника:** `Modal` или небольшой `Drawer`; название, выбор иконки из ограниченного набора (не произвольные URL). Удаление только при отсутствии задач.
- **Телефон:** сайдбар источников в `Drawer`, карточки задач вместо горизонтальной прокрутки таблицы, полноэкранная форма создания/редактирования.
- Используй Ant Design напрямую; оборачивай его компоненты только ради реального специфичного поведения приложения.
- Не добавляй элементы, попавшие в визуальные макеты случайно, если они не согласованы для MVP (например, колокольчик, массовое выделение строк, переключатели представлений).

## Работа с данными
На начальных этапах UI допустимы тестовые данные (fixtures). При подключении API использовать типизированный клиент и, если это оправданно, кеш серверного состояния; не дублировать списки задач в лишних глобальных сторах. При ответе `401` направлять на экран входа; ошибки API отображать без потери введённых в форму данных. Проверка авторизации на клиенте нужна для UX, но не заменяет защиту на сервере.

## Качество интерфейса
Проверять десктоп и ширины телефона 360/390 px, клавиатурную навигацию, ошибки форм, пустое состояние, отсутствие результатов, загрузку, контраст текста и размеры областей нажатия. Добавить тесты валидации, смены статусов и основных пользовательских сценариев.
