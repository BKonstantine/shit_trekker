# Backend — модульный монолит на Express

## Технологии
Express 5, строгий TypeScript, Zod, SQLite и Drizzle. Небольшой API, рассчитанный на Repka Pi 3 с 2 ГиБ RAM. Без Fastify, NestJS, микросервисов и публичной регистрации.

## Предлагаемая структура

```text
apps/api/
├── src/
│   ├── app.ts               # конфигурация Express, маршруты
│   ├── server.ts            # запуск и корректная остановка процесса
│   ├── config/env.ts
│   ├── db/
│   │   ├── index.ts
│   │   ├── schema/{users,sessions,tasks,sources}.ts
│   │   └── migrations/
│   ├── modules/
│   │   ├── auth/
│   │   ├── users/
│   │   ├── tasks/
│   │   └── sources/
│   ├── middlewares/
│   │   ├── require-auth.ts
│   │   ├── validate.ts
│   │   └── error-handler.ts
│   ├── lib/
│   └── scripts/create-user.ts
├── drizzle.config.ts
└── package.json
```

Внутри предметного модуля при необходимости разделяй `routes`, `controller`, `service`, `repository`, но не создавай пустые прослойки только ради структуры. Бизнес-правила — в сервисах, операции Drizzle — в репозиториях. Маршруты отвечают за проверку входных данных и сессии.

## Авторизация и безопасность
- Только `login`, `logout`, `me`; открытого API регистрации нет.
- Администратор создаёт, обновляет и отключает пользователей через **защищённую CLI-команду на сервере**. Пароли хранятся в виде солёного хеша с современным алгоритмом KDF; выбрать библиотеку с поддержкой целевой ARM-платформы. Нельзя хранить пароль в открытом или обратимо зашифрованном виде.
- Серверные сессии переживают перезапуск. Cookie: `HttpOnly`, в production — `Secure`, с корректным `SameSite`. При входе идентификатор сессии обновляется, при выходе сессия аннулируется. Ограничивать попытки входа и не раскрывать существование логина через разные сообщения об ошибках.
- Изменяющие запросы защищать от CSRF; осмысленно настраивать доверие к reverse proxy и проверять `Origin`. Не открывать широкий CORS.
- Единственный достоверный источник `userId` — проверенная сессия. При чтении, изменении и удалении задач и источников обязательна фильтрация по владельцу. Для чужого ID отвечать `404` или эквивалентом без утечки информации. При привязке чужого источника отклонять запрос, не раскрывая детали.
- Роль `admin` **не** даёт обычному API доступа к чужим задачам.
- Не логировать идентификаторы сессий, пароли, полные описания задач и корпоративные URL.

## Поведение источников
- У каждого источника собственный `id`, `userId`, `name`, `iconKey`.
- Для сайдбара возвращать число незавершённых задач: статусы `new` и `in_progress`.
- Запрещать удаление источника при наличии **любых** привязанных задач, в том числе завершённых: `409 Conflict`.

## Поведение задач
- Обязательны название, принадлежащий пользователю источник и календарная дата `deadline`; описание и ссылка необязательны. Статус по умолчанию — `new`.
- Разрешены переходы между любыми из трёх статусов. При наступлении дедлайна статус в базе не изменяется автоматически.
- Сортировка должна быть детерминированной (при равных значениях использовать вторичный критерий). Параметры фильтрации и сортировки валидируются.

## Эксплуатация
- Файл SQLite и данные сессий должны сохраняться после рестарта контейнера; включить внешние ключи, настроить `busy_timeout`. Режим WAL рассмотреть с учётом файловой системы и выбранного способа backup.
- Резервное копирование выполняется на сервере (SQLite Online Backup API или другой документированный безопасный способ). **Не копируй «вслепую» работающую БД в WAL-режиме.** Проверить восстановление. Пользовательского экспорта/импорта нет.
- Перед выбором пакетов и Docker-образов проверить архитектуру процессора, ОС и поддержку нативных модулей SQLite на ARM.
- Тесты: Vitest + Supertest для HTTP, интеграционные тесты на отдельной SQLite-базе. Критический сценарий: пользователь A не может получить список, прочитать, изменить или удалить задачи/источники пользователя B.
